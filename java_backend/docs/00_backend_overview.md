# 00 · 后端全景 —— 一个网站是怎么跑起来的

> 目标：读完这份文档，你能用自己的话，把"搜索一本书"这条链路从前端讲到数据库，讲清每个名词在哪个环节、干什么。

---

## 开场：你在浏览器里搜"图书"

假设你打开一个图书网站，搜索"Java 入门"，屏幕上很快列出一堆书。这短短 1 秒内，其实发生了这些事：

1. 你的浏览器（**前端**）把"我要搜 Java 入门"这句话，打包成一个 **HTTP 请求**，发到某台服务器。
2. 服务器上跑着一个 **后端程序**，它收到请求，理解了你想要什么。
3. 后端程序用 **SQL** 去 **MySQL 数据库**里翻：书名里带"Java 入门"的书有哪些？
4. 数据库把结果（比如 50 本书）返回给后端。
5. 后端把结果整理成 **JSON** 格式，塞进 **HTTP 响应**，发回浏览器。
6. 浏览器收到 JSON，解析出来，画成你看到的列表。

**一句话：前端负责"显示和交互"，后端负责"处理和算数据"，数据库负责"存数据"。**

---

## 三个角色，各司其职

| 角色 | 大白话 | 例子 |
|------|--------|------|
| 前端 | 用户看到的界面，负责好看、好点 | 网页、App、小程序 |
| 后端 | 界面背后的逻辑，负责"算"和"取" | 收到搜索请求、查数据、返回结果 |
| 数据库 | 存数据的地方，负责"记" | 所有书的书名、价格、库存 |

为什么要拆成三个？因为你**不能**让浏览器直接去读数据库（不安全、也做不到），也**不能让**浏览器自己扛所有数据（太大、放不下）。所以中间需要一个"中介"——就是后端。

---

## 数据库：为什么不能只用 Excel？

你可能会想：存数据用 Excel 不就行了？

Excel 的问题：

- **装不下**：几百万条数据，Excel 就卡死了。
- **多人同时用会打架**：两个人同时改一个单元格，谁算数？
- **查得慢**：要从 100 万行里找"书名含 Java 的"，Excel 得一行行扫。
- **不安全**：一个误操作就删光了，没法恢复、没法管权限。

**数据库**就是专门解决这些问题的软件：海量存储、**并发控制**（多人同时读写不乱）、**快速查询**（靠"索引"，底层是树——你学过的 BST 在这里派上用场）、**事务**（要么全成功要么全失败，不半吊子）、**备份恢复**。

而 **MySQL** 是数据库里最流行的一款——**免费、开源、稳定、Java 后端标配**。

---

## HTTP：前后端的"对话规则"

前端和后端隔着网络，怎么对话？得有个约定，这个约定就是 **HTTP**。

它规定了**请求**长什么样：

- **URL**：你要访问什么（`https://xxx.com/books?keyword=java`）
- **方法**：你想干嘛——查（GET）、增（POST）、改（PUT）、删（DELETE）
- **参数/数据**：你带了什么信息

也规定了**响应**长什么样：

- **状态码**：结果如何——200 成功、404 没找到、500 服务器出错了
- **内容**：返回给你的数据（通常是 JSON）

前后端约定好"用 HTTP、数据用 JSON"，就像两个人约定"说普通话、写信、用简体字"——能互通。

---

## JSON：传数据的"通用格式"

后端查出来的数据，怎么传给浏览器？得是一个双方都懂、跟语言无关的格式。这个格式就是 **JSON**：

```json
{
  "books": [
    { "name": "Java 入门", "price": 59.0, "stock": 30 },
    { "name": "Spring Boot 实战", "price": 89.0, "stock": 12 }
  ],
  "total": 2
}
```

就是一堆 `键: 值`，套来套去。Java 能生成它，浏览器能解析它，谁都能看懂。

---

## SQL：跟数据库"说话"的语言

后端怎么从数据库拿数据？得对数据库下命令。这个命令语言就是 **SQL**：

```sql
-- 查：找书名含"Java"的书
SELECT name, price FROM books WHERE name LIKE '%Java%';

-- 增：新增一本书
INSERT INTO books(name, price, stock) VALUES ('MySQL 实战', 79.0, 100);

-- 改：某本书降价
UPDATE books SET price = 49.0 WHERE id = 1;

-- 删：下架一本书
DELETE FROM books WHERE id = 2;
```

你接下来**第一件事就是学 SQL**——它最简单、反馈最快（敲一行就能看到数据出来），而且后面每一步都离不开它。

---

## Spring Boot：Java 写后端的"脚手架"

现在你会问：那"后端程序"到底怎么用 Java 写？

理论上，用最原始的 Java 也能写一个能收 HTTP 请求、查数据库的程序，但**特别繁琐**——要处理网络、解析请求、管理数据库连接、配置一堆东西。

**Spring Boot** 就是一个"脚手架/半成品厨房"：它把那些繁琐、重复、通用的活都替你干好了，你只需专注写"业务逻辑"（收到搜索请求 → 查一下 → 返回）。

它最大的特点（你以后会反复体会到）是 **依赖注入**——你不用自己 `new` 一堆对象，Spring 帮你管理好，你要用哪个就"注入"哪个。这个先有个印象，后面展开。

## 一张图串起全部

```
  浏览器/App                       后端程序(Spring Boot)              MySQL 数据库
  ─────────                       ────────────────────              ────────────
  你搜索"Java"    ──HTTP请求──▶    Controller 接收请求                 存着所有书
       ▲                          └─▶ Service 处理逻辑                  ▲
       │                              └─▶ Repository 查数据 ──SQL──▶   │
       │                                    ◀─── 返回结果 ─────────────┘
       │                              ◀── 打包成 JSON ──
       ◀────────── HTTP响应(JSON) ────
```

- 你点搜索 → 前端发 **HTTP 请求** → 后端 **Controller** 接住
- Controller 交给 **Service** 处理 → Service 让 **Repository** 去查库
- Repository 用 **SQL** 查 **MySQL** → 拿回结果
- 结果打包成 **JSON**，作为 **HTTP 响应** 送回前端 → 前端画出来

> **Controller / Service / Repository** 是后端代码的"三层结构"，职责分明，以后写代码就按这个分。

## 你的学习路线图

```
第 1 步：装 MySQL，学 SQL          ← 最简单、反馈最快，先学这个
第 2 步：学 HTTP + JSON            ← 理解前后端怎么对话
第 3 步：学 Spring Boot            ← 用 Java 写后端
第 4 步：做项目（图书管理系统）      ← 把所有东西串成一个能跑的网站
```
