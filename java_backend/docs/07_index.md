# 07 · 索引 —— 给数据装一个"目录"

> 目标：搞懂索引是什么、为什么能加速查询、怎么建、什么时候会失效。
> 前置：读完 01~06，会建表、增删改查；脑子里有"树 / 二分查找"的印象更好（ds_learning 阶段二学过）。

---

## 零、索引是什么？为什么需要它

一句话：**索引 = 给一张表建的"目录"，让数据库不用一行行翻，直接跳到目标数据。**

类比：查字典。没有索引 = 从第一页翻到最后一页找一个字（**全表扫描**，慢）；有索引 = 按拼音/偏旁目录直接翻到那一页（**快速定位**，快）。

现实意义：表里有几百万行数据，`WHERE name = '张三'` 如果一行行比对，要比对几百万次；有了 `name` 上的索引，只需比对几十次（O(log n)）。

> 核心思想：**拿"查找时间"换"额外空间 + 写入时间"**。索引本身要占磁盘，而且每次增删改数据，索引也要跟着更新。所以不是列越多越好。

---

## 一、索引的底层：B+ 树

MySQL 的 InnoDB 存储引擎默认用 **B+ 树（B+ Tree，平衡多路查找树）** 存索引。

你在 ds_learning 学过二叉树、BST、堆。B+ 树可以理解成它们的"远房亲戚"，专为磁盘设计：

- **多路**：一个节点不只存 2 个孩子，而是存几百个，所以树很"矮"（3~4 层就能存上千万数据）
- **叶子层排好序、用链表串起来**：既支持等值查找（`=`），也支持范围查找（`BETWEEN`、`> <`）

你不用深究 B+ 树内部，记住两个结论：

1. 有了索引，查找从 **O(n) 全表扫描** 变成 **O(log n) 树查找**——这就是它快的根本原因。
2. 索引结构是**排序**的，所以范围查询（如 `age > 20`）也受益。

## 二、索引的分类

### 按功能分（面试常考）

| 类型 | 说明 | 特点 |
|------|------|------|
| **主键索引** PRIMARY KEY | 建主键时自动创建 | 唯一、非空，一张表只能有一个 |
| **唯一索引** UNIQUE | 列值不能重复 | 可以为 NULL（多个 NULL 不算重复） |
| **常规索引**（普通索引） | 只为加速查询，没约束 | 值可重复、可为 NULL |
| **全文索引** FULLTEXT | 搜大段文本里的词 | 中文支持一般、用得少，了解即可 |

> 记忆：主键索引和唯一索引，本质是"**普通索引 + 一个唯一约束**"。

### 按结构分（InnoDB 特有）

- **聚簇索引**：数据本身按主键排序存储（主键就是聚簇索引，叶子节点存的是**整行数据**）
- **二级索引**（辅助索引）：除主键外的其他索引，叶子节点存的是**主键值**，查到主键再"**回表**"查整行

## 三、索引的语法

### 1. 创建

建表时一起建：

```sql
CREATE TABLE user (
  id INT PRIMARY KEY,              -- 主键索引
  name VARCHAR(20),
  UNIQUE KEY idx_name (name)       -- 唯一索引
);
```

给已有表加索引：

```sql
CREATE INDEX idx_user_name ON user(name);          -- 普通索引
CREATE UNIQUE INDEX idx_user_name ON user(name);   -- 唯一索引
```

### 2. 查看

```sql
SHOW INDEX FROM user;
```

### 3. 删除

```sql
DROP INDEX idx_user_name ON user;
```

> 命名习惯：索引名一般以 `idx_` 开头（idx = index 索引）。你之前见过的 `fk_user_dept_id` 是**外键约束名**，`idx_` 是**索引名**，别搞混。

## 四、索引的优缺点

| 优点 | 缺点 |
|------|------|
| 查询变快（最主要） | 占额外磁盘空间 |
| 排序、分组也变快（ORDER BY / GROUP BY 能用上索引的有序性） | 增删改变慢（要同步更新索引） |
| 保证唯一性（唯一索引） | 维护成本 |

**结论：** 给**查询频繁、且区分度高的列**建索引，别给每列都建。

---

## 五、最左前缀法则（联合索引）

**联合索引** = 多个列一起建一个索引：`CREATE INDEX idx_a_b ON t(a, b);`

它像"先按 a 排序，a 相同再按 b 排序"。所以：

- `WHERE a = 1` ✅ 用得上（用了最左边 a）
- `WHERE a = 1 AND b = 2` ✅ 用得上
- `WHERE b = 2` ❌ 用不上（跳过了最左边 a）

**这就是最左前缀法则：联合索引必须从最左边的列开始，依次往后，中间不能跳过。**

---

## 六、索引失效的场景（重点，避免踩坑）

建了索引却没用上，等于白建。常见失效：

| 场景 | 例子 | 为什么失效 |
|------|------|-----------|
| 对列做函数/运算 | `WHERE SUBSTRING(phone,1,3) = '138'` | 值被加工了，索引对不上 |
| 隐式类型转换 | `WHERE phone = 13800000000`（phone 是字符串列） | 数字 vs 字符串，MySQL 会转类型 |
| 前导模糊 | `WHERE name LIKE '%张'` | 以 % 开头，没法走有序索引 |
| 违反最左前缀 | 见上一节 | 跳过了最左列 |
| `OR` 两边有一边没索引 | `WHERE a=1 OR b=2`（只有 a 有索引） | 要回退到全表扫描 |

> 记法：**索引要"原样、从最左、非模糊开头"才能用上。**

## 七、EXPLAIN：看查询有没有走索引

`EXPLAIN` 是 MySQL 自带的"执行计划"工具，看一条查询是怎么跑的：

```sql
EXPLAIN SELECT * FROM user WHERE name = '张三';
```

关键看两列：

- **type**：访问类型，从好到差 `const`（主键/唯一等值）> `ref`（普通索引）> `range`（范围）> `ALL`（全表扫描，最差，没走索引）
- **key**：实际用到的索引名；是 `NULL` 说明没用上索引

> 以后判断"我的索引到底生效没"，就用 EXPLAIN，别靠猜。

---

## 八、设计原则（哪些列该建索引）

1. 查询频繁、区分度高的列（如身份证号、手机号；**别**给"性别"这种只有两三个值的列建，区分度太低）
2. 常出现在 WHERE / JOIN ON / ORDER BY / GROUP BY 里的列
3. 数据量大（几十万行以上）才值得建；小表全表扫描可能更快
4. 字符串列优先考虑**前缀索引**（只建前几个字符，省空间）
5. 联合索引比多个单列索引更省，但要遵循最左前缀

## 九、动手练习（用你的 user 表）

1. 给 `user` 表的 `name` 列建普通索引，`SHOW INDEX FROM user;` 看看。
2. 用 `EXPLAIN SELECT * FROM user WHERE name = '张三';` 看 type 是不是从 `ALL` 变成了 `ref`。
3. 试 `WHERE name LIKE '%张'` 和 `WHERE name LIKE '张%'`，对比 EXPLAIN 结果。
4. 建一个联合索引 `(gender, age)`，试 `WHERE gender='M'` 和 `WHERE age>20`，看哪个走索引。
5. 最后 `DROP INDEX` 删掉，恢复原样。

> 练习重点体会：**EXPLAIN 里 type 的变化**（ALL → ref）就是"索引生效"的直接证据，以及**哪些写法会让索引失效**。

---

## 怎么用（一句话）

索引 = 给表建目录，让查询从 O(n) 变 O(log n)；语法就 `CREATE / 查看(SHOW) / DROP INDEX`，核心记三点：**最左前缀法则、索引失效场景、用 EXPLAIN 验证**。
