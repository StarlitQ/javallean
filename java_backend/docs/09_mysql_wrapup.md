## 一、存储引擎

### 是什么

存储引擎 = "**表数据的存储方式 / 底层实现**"。同一张表的数据，可以交给不同的引擎去存。用 `SHOW ENGINES;` 能看 MySQL 支持哪些引擎。

一句话：**存储引擎决定这张表——怎么存、支不支持事务、支不支持外键、锁是行级还是表级。**

### 两大主流（面试重点）

| | **InnoDB** | **MyISAM** |
|---|---|---|
| 是否默认 | ✅ MySQL 5.5 起默认 | 老版本默认 |
| 事务 | ✅ 支持 | ❌ 不支持 |
| 外键 | ✅ 支持 | ❌ 不支持 |
| 锁粒度 | **行锁** | **表锁** |
| 适用场景 | 需要事务的正式业务 | 只读、日志这类 |

> 记忆：**现在默认全用 InnoDB，MyISAM 只在"老项目 / 只读场景"偶尔见。** 面试答这句 + 上表就够了。

其他引擎（MEMORY 存内存断电丢、CSV 等）了解有这回事就行，不用管。

## 二、锁

### 为什么需要锁

并发时多个事务同时改同一行数据，不加锁就会互相覆盖（丢失更新）。锁就是"**协调并发访问**"的机制——你改的时候我先锁住，别人等你改完。

### 按粒度分（面试重点）

| 锁 | 锁住范围 | 特点 |
|---|---|---|
| **表锁** | 整张表 | 简单粗暴，并发差 |
| **行锁** | 某一行 | 精细，并发好（InnoDB 默认） |

> 呼应 08：`UPDATE ... WHERE` 的 WHERE **没走索引**时，行锁会**升级成表锁**（锁整张表）。所以 UPDATE/DELETE 的 WHERE 要带索引。

### 按思想分：乐观 vs 悲观

| | **悲观锁** | **乐观锁** |
|---|---|---|
| 思路 | "肯定会有人跟我抢"，先锁 | "一般没人抢"，改完再检查 |
| 实现 | `SELECT ... FOR UPDATE` | 加一个 version 字段，更新时比对 |
| 适用 | 冲突多 | 冲突少 |

> 面试爱问这个概念，能说出"悲观先锁、乐观改完验证版本"就够。

其他（共享锁/排他锁、死锁）了解名词即可，不用深究。

## 三、视图 View

### 是什么

视图 = "**存起来的一条 SELECT**"。它**不存数据**，只是一个查询的封装，用的时候像表一样查。

```sql
-- 把常用的 JOIN 封装成视图
CREATE VIEW v_user_dept AS
SELECT u.name, d.name AS dept_name
FROM user u JOIN dept d ON u.dept_id = d.id;

-- 以后直接查视图，像查表一样
SELECT * FROM v_user_dept;
```

### 有什么用

1. **简化复杂查询**：把经常写的一大串 JOIN 封装成视图，以后查它就一行。
2. **安全 / 权限**：只把部分列暴露给用户（比如不给看身份证号）。

### 关键理解

- 视图**不存数据**，它是一层"窗口"，背后还是真实表的数据。
- 删视图 `DROP VIEW 视图名;` 只是删掉这层窗口，不动真实表。
